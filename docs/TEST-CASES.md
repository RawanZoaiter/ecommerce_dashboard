# حالات الاختبار المطلوبة + نظرة على مشروع الباك إند

كل أمر ونتيجة في هذا الملف مأخوذة من تشغيل فعلي على هذا الجهاز بتاريخ 3 تشرين الثاني 2026،
والمخرجات منسوخة كما ظهرت لا كما يُفترض أن تظهر.

**قبل أي اختبار**: شغّلي خدمة المخزون ثم الباك إند (التفاصيل في ورقة التشغيل)، وتأكدي:

```bash
curl http://localhost:8080/api/products/1
```

إن ظهر `"available_quantity"` برقم فالخدمتان متصلتان وتقدرين تبدئين.

# الجزء الأول — بنية مشروع الباك إند

## لماذا خدمتان لا خدمة واحدة

المتطلب الثاني يطلب فصل إدارة المخزون في خدمة مستقلة تتواصل مع التطبيق عبر gRPC مباشرة.
التقسيم الفعلي:

| الخدمة | اللغة | تملك | المنفذ |
|---|---|---|---|
| التطبيق الرئيسي | Laravel 12 / PHP 8.3 | المستخدمون، المنتجات، الطلبات | 8080 |
| خدمة المخزون | ASP.NET Core / C# | الكميات والحجوزات | 5275 (gRPC) |

لكل خدمة قاعدة بياناتها: لارافيل على MariaDB، والمخزون على SQL Server. لا تقرأ أي منهما
جدول الأخرى — وهذا هو جوهر الفصل، لا مجرد وجود مشروعين.

**نقطة مهمة للمناقشة**: الواجهة لا تتصل بخدمة المخزون إطلاقًا. تتعامل مع الـ REST API فقط،
ولارافيل وحده من يتكلم gRPC. هذا مذكور صراحةً في دليل الواجهة، وهو سبب كون الداشبورد لا
تحتاج أي كود gRPC.

## تقسيم الكود إلى وحدات

```
app/
├── Shared/      الرد الموحد، معالجة الأخطاء، حالة التطبيق، X-Request-ID
└── Modules/
    ├── Users/       التسجيل والدخول والـ tokens
    ├── Products/    المنتجات والتصنيفات
    ├── Orders/      الطلبات وحالاتها
    └── Inventory/   عميل gRPC الذي يكلّم خدمة المخزون
```

كل وحدة تحمل ما يخصها من Controllers و Requests و Resources و Models و Policies، ولكل
وحدة ملف `routes.php` خاص بها. وحدة الإشعارات مذكورة في الخطة ولم تُبنَ بعد.

## الشكل الموحد للرد

كل رد، نجاحًا أو فشلًا، له نفس المفاتيح الثلاثة: `code` و`message` و`data`. الرسالة
بالإنجليزية ومكتوبة للمبرمج، والواجهة تعرض نصوصها الخاصة بناءً على `code`. ولكل رد ترويسة
`X-Request-ID` تُرفق عند الإبلاغ عن مشكلة.

## المصادقة

JWT بـ `access_token` عمره ساعة و`refresh_token` عمره 30 يومًا. المهم أن **كل refresh
token يُستعمل مرة واحدة فقط**: بعد التجديد يبطل القديم. لهذا يوجد في الداشبورد قفل يمنع
إرسال أكثر من طلب تجديد في اللحظة نفسها — الملف `core/network/interceptors/refresh_interceptor.dart`.

## حماية الطلبات المكرّرة

`POST /orders` يتطلب ترويسة `Idempotency-Key` إلزاميًا. السبب: لو انقطع الاتصال بعد أن
حجز السيرفر الكمية فعلًا، فإعادة الإرسال بنفس المفتاح تُكمل الطلب نفسه بدل أن تحجز مرة
ثانية وتترك كمية محجوزة بلا طلب.

## عقد الـ gRPC

ثلاث عمليات فقط في `proto/inventory.proto`:

| العملية | متى |
|---|---|
| `GetStock` | عند عرض تفاصيل منتج |
| `ReserveStock` | عند إنشاء طلب — كل الطلب أو لا شيء |
| `ReleaseStock` | عند إلغاء الطلب، أو فشل الحفظ بعد الحجز |

**ليس فيه عملية لإضافة أو تعديل كمية.** وهذا مكتوب في العقد نفسه:

> «Provisioning inventory rows for new products is deliberately not part of this
> contract and is a separate integration decision.»

نتيجته العملية: المنتج المُضاف من اللوحة لا سجل مخزون له، فلا يمكن طلبه حتى يسجّل أحد كمية
له يدويًا. هذه ثغرة معروفة ومؤجَّلة عن قصد، لا خطأ.

# الجزء الثاني — الإثباتات المطلوبة

## المتطلب الأول: «محاولة مستخدم الوصول لطلب غيره، وتنفيذ عملية ليست من صلاحيته، تُرفض»

الإعداد: سجّلي حساب زبون، وأنشئي طلبًا باسم المسؤول، ثم حاولي الوصول إليه بتوكن الزبون.

```bash
curl -X POST http://localhost:8080/api/auth/login -H "Content-Type: application/json" -H "Accept: application/json" -d "{\"email\":\"admin@example.com\",\"password\":\"123456789\"}"
```

خذي `access_token` من الرد، ثم جرّبي الحالات التالية بتوكن الزبون.

### النتائج الفعلية

```
[PASS] customer reads another user's order        got 404, expected 404
[PASS] customer changes an order status           got 403, expected 403
       Only admins can change order status.
[PASS] customer creates a product                 got 403, expected 403
       Only admins can add products.
[PASS] guest reads an order (no token)            got 401, expected 401
       Unauthenticated.
[PASS] customer list shows only their own orders  got 0, expected 0
```

### النقطة التي تستحق الشرح في المناقشة

محاولة قراءة طلب شخص آخر ترجع **404 لا 403**. وهذا متعمَّد: لو أرجع السيرفر 403 لكان قد
أكّد أن الطلب موجود ويخص غيرك، فيستطيع أي شخص استكشاف أرقام الطلبات الموجودة بالتجربة.
الـ 404 لا تكشف شيئًا — «لا يوجد» و«ليس لك» تبدوان متطابقتين تمامًا.

والفرق بين 401 و403 مقصود أيضًا: **401** تعني «سجّل الدخول» (لا يوجد توكن)، و**403** تعني
«أنت مسجّل لكن غير مسموح». الداشبورد تعرض لكل منهما شاشة مختلفة.

وللتأكيد: الدور يُقرأ من قاعدة البيانات مع **كل** طلب، فإخفاء الأزرار في الواجهة راحة
للمستخدم لا إجراء أمني.

---

## المتطلب الثاني: «عدة طلبات في نفس اللحظة على آخر قطعة — طلب واحد فقط ينجح»

هذه معالجة الـ Race Condition، والضمانة في خدمة المخزون نفسها لا في لارافيل.

الإعداد: المنتج 3 كميته 1 بالضبط (مضبوطة في `compose.override.yaml` لهذا الغرض). أرسلي
ثمانية طلبات متزامنة، كل واحد بمفتاح `Idempotency-Key` مختلف — مفاتيح مختلفة لأنها محاولات
شراء مستقلة لا إعادة إرسال لنفس الطلب.

### النتيجة الفعلية

```
8 simultaneous orders for product 3 (stock 1)
outcomes: [201, 409, 409, 409, 409, 409, 409, 409]

[PASS] exactly one order succeeded      got 1, expected 1
[PASS] the rest were rejected with 409  got 7, expected 7
[PASS] product 3 stock is now 0         got 0, expected 0
```

واحد نجح، سبعة رُفضوا، والمخزون انتهى عند صفر بالضبط — لا سالب ولا بقايا.

### كيف تعيدين التجربة

السكربت الذي أنتج ما سبق محفوظ محليًا. ولتشغيله من جديد تحتاجين إرجاع كمية المنتج 3 إلى 1
أولًا، لأنها صارت صفرًا:

```bash
cd C:\Users\iamgh\ecommerce-inventory-service
```

```bash
docker compose down -v
```

```bash
docker compose up -d --build
```

`down -v` يمسح قاعدة المخزون، وإعادة التشغيل تزرعها من جديد بالكميات الأصلية.

### ماذا تقولين عن آلية الحماية

الحجز في خدمة المخزون يجري داخل معاملة (transaction) على صف المنتج، فالطلبات المتزامنة
تُسلسَل على مستوى قاعدة البيانات: أول من يصل يحجز، والبقية يقرأون الكمية بعد النقصان
فتُرفض. الحجز **كل الطلب أو لا شيء**: لو كان في الطلب خمسة منتجات وواحد منها ناقص، لا
يُحجز أي شيء ولا تنقص كمية أي منتج.

## حالات الفشل الثلاث

### 1. الكمية غير كافية

```bash
curl -X POST http://localhost:8080/api/orders -H "Content-Type: application/json" -H "Accept: application/json" -H "Authorization: Bearer <TOKEN>" -H "Idempotency-Key: 11111111-1111-1111-1111-111111111111" -d "{\"products\":[{\"product_id\":3,\"quantity\":99}]}"
```

يرجع `409` مع تفصيل كل منتج ناقص:

```json
{
  "code": 409,
  "message": "Some products do not have enough stock.",
  "data": {
    "insufficient_items": [
      { "product_id": 3, "name": "...", "requested_quantity": 99, "available_quantity": 1 }
    ]
  }
}
```

الواجهة تعرض هذه القائمة للزبون ليعدّل الكميات بنفسه، بدل رسالة خطأ عامة.

### 2. منتج بلا سجل مخزون

المنتج 4 موجود في قاعدة لارافيل وليس له سطر في خدمة المخزون. طلبه يرجع:

```json
{ "code": 409, "message": "One or more products are not available for ordering.", "data": null }
```

هذه هي الحالة نفسها التي يقع فيها أي منتج يُضاف من اللوحة، لأن `POST /products` لا ينشئ
سجل مخزون.

### 3. خدمة المخزون متوقفة

```bash
cd C:\Users\iamgh\ecommerce-inventory-service
```

```bash
docker compose stop inventory-api
```

بعدها:

- `GET /products/4` يرجع `available_quantity: null`
- إنشاء أي طلب يرجع `503 Inventory service is temporarily unavailable. Please try again shortly.`
- **لا يُنشأ أي طلب**، فلا يوجد ما يحتاج تنظيفًا

وللإرجاع:

```bash
docker compose start inventory-api
```

**ما تقوله الواجهة**: رسالة «الخدمة مشغولة، حاول بعد قليل» مع زر إعادة المحاولة، وزر
الإعادة يرسل **نفس الطلب بنفس الـ Idempotency-Key** تمامًا — وهذا هو بيت القصيد: لو كان
السيرفر قد حجز الكمية فعلًا قبل أن ينقطع، فإعادة الإرسال بنفس المفتاح تُكمل الطلب نفسه ولا
تحجز مرة ثانية.

> تنبيه: الرد قد يتأخر حتى 3 ثوانٍ قبل أن يرجع 503، لأن هذه هي مهلة لارافيل في انتظار
> المخزون. لذلك الواجهة تعطّل زر الإرسال أثناء الانتظار.

### 4. فشل الحفظ بعد الحجز

الحالة الثالثة في الصورة: نجح الحجز ثم فشل حفظ الطلب. لا تُختبر يدويًا — تتطلب إسقاط قاعدة
لارافيل في اللحظة بين العمليتين. المعالجة موجودة في الكود: لارافيل ينادي `ReleaseStock`
بنفس `reservation_id` فترجع الكمية. وإن تعذّر ذلك لحظتها، يعيدها لاحقًا عبر مهمة مجدولة:

```bash
docker compose --profile scheduler up -d scheduler
```

## ما يخص الداشبورد تحديدًا

| المطلوب | أين يظهر |
|---|---|
| عرض الكمية المتوفرة | صفحة تفاصيل المنتج |
| تصفية حسب التصنيف | أعلى جدول المنتجات |
| تقسيم صفحات | أسفل كل جدول، بأرقام من `meta` |
| إضافة منتج مع صورة | زر «إضافة منتج» |
| تغيير حالة الطلب | صفحة تفاصيل الطلب، بالانتقالات المسموحة فقط |
| رفض ما ليس من الصلاحية | شاشة مختلفة لـ 401 و403 |

**الشاشات المحذوفة**: المخزون والمستخدمون والإشعارات كانت موجودة على بيانات تجريبية
وحُذفت، لأنها بلا endpoints. تعود حين تُبنى. وكذلك حُذف من الصفحة الرئيسية عدّاد الإيرادات
وعدّاد المخزون المنخفض: الأول يحتاج مجموع كل الطلبات ولا يوجد endpoint له، والثاني يحتاج
الكمية في قائمة المنتجات وهي غير موجودة فيها. عرض رقم تقريبي يبدو موثوقًا وهو خاطئ أسوأ من
عدم عرضه.

## ما ينقص من الـ API

| المطلوب | الأثر |
|---|---|
| `available_quantity` في `GET /products` | لا عمود كمية في الجدول ولا عدّاد مخزون منخفض. `GetStock` تأخذ منتجًا واحدًا، فالقائمة تحتاج عملية batch في الـ proto لا حقلًا فقط |
| مسار لتعديل المخزون | المنتج المُضاف من اللوحة غير قابل للطلب. يحتاج عملية جديدة في الـ proto **وفي** خدمة الـ .NET، لا endpoint في لارافيل فقط |
| `inventory` في `GET /app-status` | `available_quantity: null` تعني «الخدمة متوقفة» أو «لا سجل مخزون»، ولا شيء يفرّق بينهما |
| `GET /users` | وحدة المستخدمين من الوحدات الأربع المذكورة في المتطلبات ولا endpoint لها |
| `GET /notifications` | الإشعارات مذكورة في الخطة ولم تُبنَ |
| `GET /admin/stats` | أرقام الصفحة الرئيسية تأتي من ستة نداءات بدل واحد |
| `?search=` في `GET /products` | لا بحث بالاسم؛ حقل البحث في الواجهة لا يُرسَل للسيرفر |
